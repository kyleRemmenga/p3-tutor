Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context at each step, what gets saved between sessions, and how it finds the right page in a long manual.

Warm-up 2 min

Recall

Without looking back: in the agent loop, what happens right after the model asks for a tool, and what happens to the result?

Check your answer

The program around the model runs the tool. The result is then given back to the model, which decides on the next action or writes the final answer. This lesson is about that last part: exactly what the model is shown each time the result goes back.

What the model sees: the context 5 min

Start with a concrete case. A student types: "Is the laser cutter free Friday afternoon, and do I need training?" Your assistant calls check_calendar, and the calendar returns three bookings. Now the program must call the model again to decide what to do next.

Here is the key fact. The model remembers nothing from its previous call. Each call is a fresh start, and the model only knows what the program puts in front of it. Everything it is given in one call is called the context: Anthropic defines it as "the set of tokens included when sampling from a large-language model" (Anthropic, Effective context engineering for AI agents). A token is a small chunk of text, often a word or part of a word. The context window is the maximum number of tokens the model can take in at once, the text you send plus the text it writes back.

For your assistant, the context at the second call might look like this:

[system prompt]  You are the makerspace assistant. Rules: ...
[tool list]      check_calendar(machine, date), search_manuals(query), ...
[student]        Is the laser cutter free Friday afternoon, and do I need training?
[model]          (request) check_calendar("laser cutter", "Friday")
[tool result]    Booked: 09:00-11:00, 12:00-13:00, 17:00-19:00
                 <- the model is called again with all of the above

The program builds this list. The model's job is only to read it and write the next piece.

A common mix-up

"The model remembers the conversation." It feels true, because chatbots seem to remember. But the chat app is re-sending the earlier messages with each new one. Delete a message from what you send, and the model has no trace of it. That is why "memory" in an agent is always something your program builds, never something the model has.

Check yourself

The assistant answered a student's question yesterday. Today the program starts a new request and sends only today's question, with the system prompt and tools. What does the model know about yesterday?

Show the answer

The third option. The model sees only the context it is given. Yesterday's chat is gone unless the program saves it somewhere and puts it back in.

What is kept between steps 5 min

Inside one request, the agent runs several steps (several model calls). What carries from step to step? Only the list the program keeps. A simple agent just appends to it: each model output and each tool result is added to the end, and the whole list is sent again at the next step.

messages = [system_prompt, user_question]
while True:
    reply = call_model(messages, tools)      # a fresh call each time
    messages.append(reply)                   # keep what the model said
    if reply is final_answer:
        break
    result = run_tool(reply.tool_request)    # the program runs the tool
    messages.append(result)                  # keep what came back

This list is the agent's working memory for the request: it lasts as long as the request and is lost when the program stops. Lilian Weng's survey of agents calls this kind of in-context information the agent's short-term memory, limited by the context window (Weng, LLM Powered Autonomous Agents).

Notice what this means for cost. The list grows each step, and every call re-sends all of it. If a laser cutter manual page of 3,000 tokens is fetched at step 2, it is paid for again at step 3, step 4 and every step after. Cost therefore grows faster than the number of steps, which matters on your sponsor's budget.

Some providers discount repeated, unchanged beginnings of a prompt ("prompt caching"). That is a pricing detail to check later; the point here is that the model still reads all of it.
Check yourself

A request takes 5 steps. A 2,000-token tool result arrives after step 1 and stays in the list. In how many model calls does the model read those 2,000 tokens?

Show the answer

Four. The result exists only after step 1, so the calls that follow (steps 2 to 5) each re-read it.

Why the window is a budget 5 min

Two limits apply to the context, and a good design respects both.

  • A hard limit. The window has a maximum size. If the list grows past it, the call fails or something must be cut.
  • A soft limit. Even before the window is full, more text can make the model worse. Anthropic calls this context rot: as the number of tokens grows, "the model's ability to accurately recall information from that context decreases." It describes the model as having an "attention budget" that each new token uses up (Anthropic).

So the goal is not to fill the window. Anthropic's guidance is to find the smallest set of high-signal tokens that makes the right outcome likely. For you, that means: do not paste whole manuals into the context.

When a long task does outgrow the window, there are three standard tools (Anthropic):

TechniqueWhat it doesMakerspace example
CompactionSummarize the conversation so far and start a new context with the summary.A long booking chat becomes: "Student wants the 3D printer Thursday; training confirmed; chose 2 pm."
Tool-result clearingDrop old, bulky tool outputs that have already been used.Remove the full calendar listing once the answer is known.
Sub-agentsGive a focused job to a separate model run with its own clean context, and take back only a short summary.One run reads three manuals and returns five lines. (Lesson on multi-agent systems comes later.)
A common mix-up

"A bigger context window solves memory." It is tempting: a window that holds a whole manual sounds like the end of the problem. But a bigger window means a higher bill per call, since every token is read every call, and context rot still applies. A bigger window raises the hard limit; it does not remove the need to choose what goes in.

What is kept between sessions: notes 6 min

Working memory dies when the request ends. But your assistant must remember that Maya passed the laser cutter training last month. That needs long-term memory: information stored outside the context window, which survives between sessions.

The simplest design is the one Anthropic calls structured note-taking: the agent "regularly writes notes persisted to memory outside of the context window," which are pulled back in later. Their examples include a to-do list and a NOTES.md file (Anthropic). This tutoring workspace works the same way: I read NOTES.md at the start of each session because I remember nothing from the last one.

Anthropic's API offers a ready-made version, the memory tool. Claude asks to view, create or edit files under a /memories folder, and your application carries those requests out: "Memory lives entirely in your application." The files persist between sessions only because your code stores them somewhere (Claude docs, memory tool). It is the agent loop again: memory is a tool the model calls.

Design questions for you, which this lesson cannot answer for you but your design review will ask:

  • What to save. Facts that stay true and matter later (training status), not the whole chat.
  • Whose notes. One file per student, so one student's data never lands in another's context.
  • Who writes. For training status, the booking system's database is the source of truth; a model-written note could be wrong. Consider a tool that reads the record rather than a note the model wrote itself.
  • Safety. The docs warn that a path such as /memories/../../secrets.env can escape the memory folder, so your code must validate every path.

Retrieval: finding the right page 5 min

Notes cover what the assistant learns. The manuals are different: they are large, fixed, and written by someone else. A laser cutter manual may run to hundreds of pages. You cannot send all of it each call (cost, context rot), so the program must retrieve only the few passages relevant to the question and put those into the context. This is memory as lookup.

Anthropic describes the approach as just-in-time retrieval: the agent keeps "lightweight identifiers (file paths, stored queries, web links, etc.)" and loads data into context only when needed, using tools (Anthropic). Your search_manuals(query) tool is exactly this.

How does the tool find the right page? Two common ways:

  • Keyword search. Match the words in the question to the words on the page. Fast and exact; it misses pages that use different words ("kerf" versus "cut width").
  • Embedding search. An embedding turns a piece of text into a list of numbers so that texts with similar meaning get similar numbers. The tool compares the question's numbers to each page's numbers and returns the closest. Weng describes this as long-term memory held in an external vector store with fast retrieval (Weng). It finds "cut width" for "kerf", but can miss an exact part number.

Before search can work, manuals are split into chunks, pieces of a page or two with a heading each. Chunks that are too big waste context; too small, and they lose the surrounding explanation. A reasonable first design returns the top three chunks, each labeled with manual and page so that the answer can cite it.

You do not need the maths inside embeddings for this mission. Treat the embedding step as a black box that scores "how related are these two texts".
A common mix-up

"Retrieval makes the answer true." Retrieval only puts text in front of the model. If the wrong chunk comes back, the model will write a confident answer from it. Bad retrieval is a main source of wrong answers in systems like yours, so test search on real student questions. You noticed in chatbots that a model can state an outdated fact with confidence; retrieved text from an old manual edition does the same.

Check yourself

A student asks about the "kerf" setting, but the manual only ever says "cut width". Which search is likelier to return the right chunk, and why?

Show the answer

Embedding search. Keyword search would find nothing for "kerf" because the page never uses that word.

Worked example and practice 5 min

Worked example

Design the memory for one request: "Can I use the CNC router on Saturday? I did the intro safety course in October."

  1. List every piece of information needed. Router booking on Saturday; the student's real training status; the router's training rules; the student's claim about October.
  2. Sort each piece by how it changes. The calendar changes hourly, so fetch fresh with check_calendar. The training status is a stored fact, so load it from the student's record. The rules sit in the manual, so retrieve them with search_manuals. The student's claim stays in the context for this request only.
  3. Decide what enters the context up front. Only the system prompt, tool descriptions, the question and the student's id. Everything else comes in on demand.
  4. Decide what is saved afterward. If a new booking was made, the booking system records it. Nothing else needs saving; the student's claim is not trusted as a fact.
  5. Check the size. Three retrieved chunks, one record and one calendar result: a few thousand tokens, instead of a whole manual.
Your turn

A student writes: "Is the vinyl cutter free Tuesday? I always use the 24-inch roll, so remind me what blade depth the manual says for it." Step 1 is done for you: the information needed is the Tuesday calendar, the student's preference ("always uses the 24-inch roll"), and the blade-depth guidance. Sort each piece into: fetch fresh with a tool, load from saved notes, retrieve from the manual, or keep only in this request's context. Then say what, if anything, to save afterward.

Show a solution

Tuesday calendar: fetch fresh with check_calendar, because it changes. Blade depth: retrieve from the vinyl cutter manual with search_manuals. "Always uses the 24-inch roll": this is a durable preference, so it fits a per-student note, and it can be loaded at the start (or saved now if absent). The question wording stays in this request only. Afterward, save the roll preference if it was not already stored; do not save the calendar result.

Summary 2 min

  • The model has no memory of its own. Its context is whatever the program sends in each call, and the window is a size limit on it.
  • Between steps, the program's growing message list carries the state; every call re-reads it, so cost and context rot grow with it.
  • Between sessions, only what is stored outside (notes, records) survives; the program loads it back into the context.
  • Retrieval pulls the few relevant chunks of a long manual into the context just in time, instead of loading everything.
