Context and memory: what the assistant sees, keeps and looks up

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a store the assistant searches.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Those are three separate memory decisions, and you will defend them at your design review. This lesson gives you the vocabulary and a rule of thumb for each.

The context window 5 min

A concrete example first

Think of a student at a desk with a fixed-size desk. They can only work with papers that are on the desk. Anything in a cabinet across the room does not exist for them until someone fetches it. The desk has a size limit, and every paper on it takes up room, including the instructions they were given and the answer they are writing.

A language model works like this. Everything it can use for a single reply must be written into one block of text sent in that call. That block is the context. The context window is the maximum size of the context, measured in tokens. A token is a small piece of text, often a short word or part of a word; as a rough guide, a page of text is several hundred tokens. The window is the size of the desk (Claude documentation: context windows).

What is on the desk for the makerspace assistant? Five things:

  • the system prompt: your instructions and rules for the assistant;
  • the tool descriptions: the text that tells the model which tools exist;
  • the conversation so far: the student's messages and the assistant's replies;
  • the tool calls and tool results from this request, such as calendar entries or a manual page;
  • the space left for the reply that the model is about to write.

Why it is also a cost

You pay by the token, for the text sent in and the text written out, so a bigger context costs more on every call. Your sponsor's budget makes this the most practical fact in the lesson. A related point from Anthropic's engineering team: more is not always better, because models have a limited "attention budget", and the goal is the smallest set of high-signal tokens that gets the result you want (Effective context engineering for AI agents). A window that can hold a whole textbook does not mean you should fill it.

Exact window sizes and prices change as models change, so this lesson gives no numbers. Look them up in the current documentation when you pick a model.

What is kept between steps 5 min

In your agent loop, every step is a separate model call. Here is the surprising part: the model does not remember the previous call. Between calls it keeps nothing. The model is stateless: it only knows what is written in the context you send this time.

So how does the assistant seem to remember that it already checked the calendar? Your program keeps a list of messages, adds each new item to the end, and sends the whole list again on the next call. The "memory between steps" is that list, held by your program.

Example: one request, step by step

Student: "Is the laser cutter free tomorrow at 3 pm, and do I need training?"

  1. Call 1. Sent: system prompt, tool descriptions, the question. The model asks for check_calendar.
  2. Call 2. Sent: all of call 1, plus the model's request, plus the calendar result. The model asks for check_training_record.
  3. Call 3. Sent: everything from call 2, plus the training result. The model writes the final answer.

Two consequences follow. First, anything that is not on the list is gone for the model: if your program drops the calendar result, the model cannot recall it. Second, long agent runs get expensive because the early part of the list is paid for again at every step. (Providers offer ways to make repeated text cheaper, such as caching; see the documentation when you reach the budget stage.)

A common mix-up

"The model remembers what happened earlier, because it was just talking about it." It is tempting because the replies sound continuous. But the continuity is made by your program re-sending the text. Test it: if you send the second call without the first call's messages, the model has no idea what was asked.

Check yourself

On step 4 of a request, the assistant gives a wrong answer about a booking it looked up in step 2. Which is the most likely cause?

Show the answer

The first option. The only memory between steps is the list your program sends. When an answer ignores earlier information, look first at what was actually sent.

When the context fills up 5 min

Because the list only grows, a long request or a long chat will eventually hit the window limit or the budget. Your program, not the model, has to decide what to do. There are three common moves, from simplest to richest.

MoveWhat it doesRisk
TrimDrop the oldest messages or old tool results.May drop something the student said that still matters.
CompactAsk the model to summarize the history, then continue with the summary in place of the full text.The summary may omit a detail you later need.
OffloadWrite bulky data to a file or store, and keep only a short pointer in the context.Needs a tool to fetch it back.

Compaction is the name for summarizing a conversation that is near the limit and restarting with the summary; Anthropic describes it, along with note-taking and sub-agents, as a technique for long tasks (Effective context engineering for AI agents).

For the makerspace assistant, a simple rule works well: keep the system prompt and tool descriptions always; keep the student's messages; and shrink old tool results first, because a calendar lookup from ten steps ago is rarely needed again in full.

Between sessions: notes 6 min

Everything so far lives and dies with one conversation. When the student closes the chat, your program's list is gone, and the next visit starts with an empty context. That is the answer to the warm-up question.

To remember across visits, the assistant needs persistent memory: information saved outside the context, in a file or database, that a later session can read. The simplest form is notes: short facts the assistant writes down, then reads back at the start of the next session. Anthropic describes structured note-taking as agents regularly writing notes to memory outside the context window and pulling them back in later (Effective context engineering for AI agents).

Here is the idea at the smallest scale, in Python you can already read:

import json

def load_notes(student_id):
    try:
        with open(f"notes/{student_id}.json") as f:
            return json.load(f)
    except FileNotFoundError:
        return {}

def save_note(student_id, key, value):
    notes = load_notes(student_id)
    notes[key] = value
    with open(f"notes/{student_id}.json", "w") as f:
        json.dump(notes, f)

# start of a session: put the notes into the context
notes = load_notes("s1234")
system_prompt += "\nKnown about this student: " + json.dumps(notes)

Memory here is just ordinary code: write to a file at the end, read from it at the start, and put what you read into the context. The model only ever sees what you put there. You can also give the model a save_note tool and let it decide what is worth keeping, which matches the loop you already know.

What deserves a note?

Notes cost context tokens every session, so keep them short and useful. For the makerspace:

  • Save: which machines the student is trained on, and the date; a stated preference, such as "mostly uses the 3D printers".
  • Do not save: the whole chat; a booking that already happened; anything the booking system already stores and can be asked again.

That last point matters. If a fact lives in another system, such as the calendar, a saved copy can go stale and disagree with the truth. Let the assistant look it up with a tool instead.

A common mix-up

"A bigger context window means the assistant remembers students." A larger window only lets one conversation hold more text. When the conversation ends, the window is empty again. Remembering across visits is a separate job, done by saving and reloading, as in the code above.

Retrieval: finding the right page 6 min

The machine manuals are the other memory problem. They are far too long to put in every context, and most pages are irrelevant to any one question. The answer is retrieval: keep the manuals in a store outside the context, and when a question arrives, find the few passages that matter and put only those into the context. Anthropic lists retrieval, tools and memory as the augmentations that turn a plain model into the basic building block of an agent system (Building effective agents).

Concretely, a manual is split into chunks (for example, one section each). When the student asks, "What speed should I cut 3 mm acrylic at?", a search_manuals tool looks through the chunks and returns the best few. Only those enter the context. The student's question tells you what to look for; the tool result is the "paper fetched from the cabinet".

How does the search find the right chunk?

There are two common approaches. Keyword search matches the words in the question to words in the chunks; it is simple, cheap and good for exact terms such as part names or error codes. Embedding search turns text into lists of numbers so that chunks with similar meaning end up close together; it can find "cutting speed for acrylic" even when the manual says "feed rate for PMMA". Many systems combine both. For a first version of your assistant, start with keyword search and add the other only if you see it miss questions you care about. This keeps the design simple, in the spirit of Anthropic's advice to start simple and add complexity only when it helps (Building effective agents).

Retrieval can still go wrong: if the search returns the wrong chunk, the model may answer confidently from it. This is why your tool should return the manual name and section with each chunk, so the answer can cite its source and a student can check.

Notice the pattern: retrieval is also "just in time". Instead of loading everything up front, the agent fetches what it needs when it needs it. Anthropic describes this approach for agents that keep light references and load data through tools as they go (Effective context engineering for AI agents).

Worked example and practice 5 min

Now put the three kinds of memory together. For each piece of information, ask: Does it need to be in front of the model on every step (context)? Does it need to survive after the chat (notes)? Is it too big or too rarely needed to carry around (retrieval)?

Worked example

Place these three items: (1) the rule "never book a student on a machine they are not trained on", (2) the full text of the soldering station manual, (3) the fact that a student finished the soldering training on 3 March.

  1. The rule. It applies to every request and is short, so it belongs in the system prompt: always in the context.
  2. The manual. It is long, and only a few paragraphs matter for any question. It belongs in a store, reached by search_manuals: retrieval.
  3. The training date. It is about one student and must survive after the chat. It goes in that student's saved record. Because the training system may already hold it, the safest design is a tool that reads it, with a note kept only for anything the assistant itself learned.
Your turn

Place these three items in the same way. Start with the first and finish the rest yourself. (1) The tool results from the current request's calendar lookup, once the booking is made. (2) The student's statement, "I'm left-handed, so please tell me which side the guard is on." (3) The 400-page printer service manual.

Show a solution

(1) The calendar result is needed for the next few steps, so it stays in the context for this request. Once the booking is done, it is a good candidate to trim or compact, and it should not become a note because the booking system already holds the truth. (2) A stated preference useful on later visits is a good note; for this one request it also stays in the conversation context. (3) The service manual is a retrieval store: chunk it and search it.

Before your review, try one more thing on paper: write your own table with three columns (context, notes, retrieval) and list at least four things the assistant knows. If you struggle to place one, that is the question to bring to the chat.

Summary 2 min

  • The model sees only the context: system prompt, tools, history and tool results, limited by the window and billed by the token.
  • The model is stateless. Memory between steps is the message list your program re-sends, so it grows and gets trimmed, compacted or offloaded.
  • Memory between sessions is saved outside the context, such as notes, and loaded back in; it needs your code.
  • Retrieval keeps big sources out of the window and brings in only the few chunks a question needs.
