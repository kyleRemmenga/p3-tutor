Context and memory in an agent

By the end of this lesson you can say, for each thing your makerspace assistant needs to know, whether it belongs in the context window, in saved notes, or in a searchable library, and why.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop (objective O1)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits. Both are memory problems, and both cost money, because every word the model reads is paid for. At your design review, "what does it keep, what does it save, how does it find the right page?" is a question you will be asked.

Warm-up 2 min

Recall

From the agent loop: the model has just asked for check_calendar for the laser cutter. Who actually runs that tool, and what happens to the result?

Check your answer

The program around the model runs the tool. It then puts the result into the model's next input and calls the model again. That last part is today's topic: "the model's next input" is the context, and what goes into it is a design decision you make.

The context window 6 min

A concrete example first

A student types: "Can I use the laser cutter tomorrow at 3 pm?" Before your model writes a single word, the program builds one long piece of text and sends it. It might contain:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Be brief. Never book without confirming.");
  • the tool descriptions: the name, purpose and parameters of check_calendar, search_manuals and book_machine;
  • the conversation so far: the student's messages and the assistant's replies;
  • the tool results that have come back during this request.

All of that, together, is the context: the text the model reads when it produces its next output. Anthropic's engineers define it the same way, as the set of tokens included when sampling from a language model (Anthropic, Effective context engineering for AI agents).

The general idea

A token is a small chunk of text, often a word or part of a word; models read and write text in tokens. The context window is the most tokens a model can take in at once, input and output together. Two facts follow, and both matter for your budget:

  1. The window is a hard limit. If your system prompt, tools, history and a 60-page manual do not fit, something has to be left out.
  2. Everything in the window is read, and paid for, on every call. Usage is billed by tokens, and each step of the loop is a separate model call. A long context is not paid for once; it is paid for again at each step.
A common mix-up

"The model remembers our conversation." It is tempting because chatbots feel like they do. But the model itself keeps nothing between calls: it takes text in and writes text out. What looks like memory is the program re-sending the earlier text each time. If the program does not include something, the model has never seen it. Likewise a bigger window does not mean automatic memory of past users; it only means more fits in one call.

Check yourself

Your assistant's system prompt and tool descriptions together take 2,000 tokens. A request takes 5 model calls. Roughly how many of those 2,000-token blocks are read in total, across the request?

Show the answer

Five. Every model call receives the whole context, including the fixed parts, so a long system prompt is a cost multiplied by the number of steps.

What is kept between steps 6 min

Within one request, the thing that carries information from step to step is the context itself. The loop you learned appends: the model's tool request, then the tool's result, then the next call sends everything. The transcript (the running list of messages, tool requests and results) is the agent's short-term memory. Nothing else carries over.

This is simple and powerful, and it has two problems.

Problem 1: it fills up

Suppose search_manuals returns three full pages of text, about 3,000 tokens, every time it is called. After five searches, 15,000 tokens of manual text sit in the context, and most of it is no longer needed once the answer is written. Anthropic describes a feature that removes stale tool calls and results from the context as it nears the limit (Anthropic, Managing context on the platform).

Problem 2: more is not always better

Anthropic's engineers point out that a model's ability to recall information from its context decreases as the number of tokens grows, and they describe the goal as the smallest set of high-signal tokens that makes the wanted outcome likely (Anthropic, Effective context engineering). So dumping the entire manual into the context is not only costly, it can make answers worse.

What is kept between sessions: notes 6 min

A session is one conversation, from the first message to the end. When it ends, the context is gone. The next time Maya (a student) opens the assistant, the window starts empty: it does not know she passed the laser-cutter training last week.

The fix is the same one you use with your own notebook. The program saves the facts that matter outside the model, and loads them into the context when the next session starts. This is notes as memory. The model is the same and keeps nothing; the notes persist because your program stores them.

Anthropic's memory tool follows this pattern: it lets Claude store and look up information outside the context window, using files (Anthropic, Managing context on the platform). You can build the same thing in plain Python, with no special tool:

# notes/maya.json  (saved by the program, outside the model)
{"trained": ["laser_cutter", "3d_printer"],
 "prefers": "afternoon slots",
 "last_booking": "laser_cutter, Fri 3 pm"}

# at the start of a session, the program does:
notes = json.load(open("notes/maya.json"))
system_prompt += "\nKnown about this student:\n" + json.dumps(notes)

# when the model learns something worth keeping, a tool saves it:
def save_note(student, key, value): ...

What deserves a note

Save facts that are durable (still true next week), costly to re-learn (asking Maya again is annoying), and small. Do not save the whole transcript: it is large, mostly noise, and you would pay to read it every session.

Notes also have a safety side. Training status decides whether someone may use a saw. Treat it as a record from your own system, written by your program from the training database, not something a student can set by typing "I'm trained." Who is allowed to write a note matters as much as what it says.

Check yourself

Which item should the assistant save as a note for the next session?

Show the answer

The training fact: durable, small and useful in later sessions. The transcript is too big and the weather remark will not matter again.

Retrieval: finding the right page 7 min

The laser cutter manual may be 80 pages; all your manuals together may be thousands. They do not fit in the window, and you would not want to pay for them on every call anyway. A student asks, "What settings do I use to cut 3 mm acrylic?" Only one paragraph answers it.

Retrieval means searching a library outside the model and putting only the best matches into the context. Retrieval-augmented generation (RAG) is the name for answering with retrieved text. A typical setup, prepared once before any student asks:

  1. Split each manual into chunks: pieces of a paragraph or a section, small enough to be useful on their own.
  2. Turn each chunk into an embedding: a list of numbers that represents its meaning, so that chunks about similar things end up close together.
  3. Store the embeddings in an index.

Then, for each question: embed the question the same way, find the few closest chunks, and put just those into the context.

Retrieval as a tool

In an agent, retrieval is usually just another tool: search_manuals(query). The model decides when to search, reads what comes back, and can search again with different words if the first result missed. Anthropic describes this as loading data "just in time" with tools instead of putting everything in the context up front (Anthropic, Effective context engineering). Chunk size and the search method are design choices that change answer quality, and research comparing RAG setups treats them as such (Wang et al., Searching for Best Practices in Retrieval-Augmented Generation).

A common mix-up

"Retrieval means the model has read the manuals." It has not. Retrieved chunks enter the context for this call and are gone when the context is cleared. And if the search returns the wrong chunk, the model answers from the wrong text, confidently. Retrieval moves the problem from "does the model know?" to "did the search find the right page?" Test the search separately.

Check yourself

The assistant answers "use 80% power" for acrylic, but the manual says 60% for 3 mm. The right page exists in the index. What is the most likely first thing to check?

Show the answer

Look at what the search returned. If the right chunk was not among them, fix chunking or search; if it was there and the model ignored it, the problem is in the prompt or context.

Worked example

Maya writes: "Book me the laser cutter Friday at 3 pm. I did the training last week. Also what's the max cut thickness for plywood?" Where does each piece of information live?

  1. "Did the training last week" is a claim about safety. The program checks the saved note (or training database) rather than trusting the message. Notes, written by the system.
  2. "Friday at 3 pm" and the machine are needed only for this booking. They go in the context as the student's message, and into check_calendar as arguments.
  3. The calendar result comes back and joins the context for the next step. After booking, it can be cleared. Context, then dropped.
  4. "Max cut thickness for plywood" is in an 80-page manual. Call search_manuals, put the top two or three chunks in the context, answer from them. Retrieval.
  5. After the session, save the new booking to Maya's note (last_booking), not the chat. Notes.
Your turn

A different student, Jon, writes: "Last time you said I prefer mornings. Book the 3D printer Tuesday, and how do I change the filament?" The first step is given: the preference is a durable fact about Jon. Place the other three things: the Tuesday booking details, the filament instructions, and what to save at the end. Say which kind of memory each uses and why.

Show a solution

1. Jon's preference: a note, loaded at the session start (given). 2. Tuesday booking details: context, passed to check_calendar and book_machine as arguments. 3. Filament instructions: retrieval from the 3D printer manual with search_manuals, with only the matching chunks placed into the context. 4. At the end: save the booking to Jon's note; leave out the filament text and the chat. Notice that "last time you said..." only works because the program saved a note and loaded it. The model has no memory of last time.

Summary 2 min

  • The model keeps nothing between calls. The context is everything it reads on this call, and it is re-sent and re-paid at every step.
  • Between steps, the transcript is the memory. Manage it by returning less, clearing stale results and summarizing.
  • Between sessions, notes saved by your program, small, durable and written by trusted code, are loaded at the start.
  • Retrieval finds the few chunks of a large library that belong in the context for this question.

Say it in your own words: without looking, explain to a teammate why the assistant can greet a returning student by what they trained on, even though the model remembers nothing.
