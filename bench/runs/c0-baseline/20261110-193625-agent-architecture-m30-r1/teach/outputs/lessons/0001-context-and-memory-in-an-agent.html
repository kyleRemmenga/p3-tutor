Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a document the assistant looks up on demand.

The context window: what the model sees 5 min

Start with a concrete case. Your assistant gets this question: "How do I change the blade on the band saw?" Before the model writes a word, the program assembles a block of text and hands it over. It holds:

  • the system prompt: "You are the makerspace assistant. Answer from the manuals. Never book without confirming."
  • the tool descriptions: check_calendar, search_manuals, book_machine;
  • the student's question.

That block is everything the model has to work with. It cannot see anything else: not the booking system, not yesterday's chat, not the manual on the shelf.

Two terms. A token is a small piece of text, often a short word or part of a word; models read and write text in tokens, and you are billed by them. The context is "the set of tokens included when sampling from a large-language model" (Anthropic, context engineering). The context window is the limit on how much the model can look at in one call: all the text it can reference when generating a response, including the response itself (Claude docs, context windows).

Everything in the request counts toward that limit: the system prompt, every message, tool results, and the tool definitions, plus the model's own output (Claude docs). So the tool descriptions you write for your team's assistant are not free. They are in every single call.

A common mix-up

"The model knows the manuals, or the booking system, because it is connected to them." It is tempting because a tool call feels like the model reaching out. But as you saw in the agent loop, the model only writes a request; the program runs it. The model knows only what is in its context, plus whatever general patterns it learned in training. Your manuals are not in training. They have to be put into the context, one way or another. The rest of this lesson is about those ways.

Between steps: the transcript is resent 6 min

Now the puzzle from the warm-up. Each model call is separate, yet at step 3 the model "knows" what the calendar returned at step 2. How?

Because the program sends it again. The model keeps nothing between calls. Each turn has an input part, which is all previous history plus the new message, and an output part that "becomes part of the input for the next turn" (Claude docs). In an agent, the program keeps the running list of messages, called the transcript, and sends the whole list on every call. What the agent "remembers" between steps is exactly what the program chose to put back in the list.

Worked example: what one request costs

The student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The system prompt, tool descriptions and question come to 2,000 tokens. Each tool request and result adds about 1,000 tokens. (These numbers are made up to show the pattern; yours will differ.)

  1. Call 1. The model sees 2,000 tokens and asks for check_calendar.
  2. Call 2. The program resends the 2,000 plus the new 1,000: 3,000 tokens in. The model asks for check_training_record.
  3. Call 3. 4,000 tokens in. The model writes the answer.
  4. Total input processed: 2,000 + 3,000 + 4,000 = 9,000 tokens, not the 4,000 you might guess from the final size.

The window grows with every step, and the early text is paid for again on every later call. Cost grows faster than the number of steps. (Features such as prompt caching can make the repeated part cheaper, but the tokens still occupy the window: "caching changes cost, not whether tokens count," per the Claude docs.)

A common mix-up

"The model remembers our conversation, so memory is automatic." It is tempting because chat apps feel that way. But a model call remembers nothing; the app around it resends the history. In your own assistant, you write that program, so what is kept between steps is your choice. That is good news: you can decide what stays in, what gets trimmed, and what a long tool result is reduced to.

When the window fills up 5 min

There are two problems here, and they are different.

A hard limit. If the input alone is over the window, the API refuses the request with an error (Claude docs). Windows today are large, but a few full manuals plus a long chat can still reach them.

A soft decline, well before the limit. Anthropic calls it context rot: as the number of tokens grows, the model's ability to accurately recall information from the context decreases. The article stresses that context is "a finite resource with diminishing marginal returns" and describes the decline as "a performance gradient rather than a hard cliff" (Anthropic). So a bigger window is not a free fix. The goal they give is "the smallest possible set of high-signal tokens" for the job.

Three common remedies, from lightest to heaviest:

RemedyWhat it doesMakerspace example
Clear old tool resultsDelete bulky results the agent no longer needsDrop the full calendar dump once the answer "free at 3 pm" is known
CompactionSummarize the conversation, then start a fresh window with the summaryAfter a long booking chat, keep "booked laser cutter Fri 3 pm; student still needs training" and drop the rest
Sub-agentHand a side task to a separate agent with its own clean window; only a short summary comes backOne helper reads three manuals and returns a 200-word answer

Compaction means "summarizing its contents, and reinitiating a new context window with the summary"; the model keeps things like decisions and unresolved problems and discards redundant tool output (Anthropic). The same article suggests tuning it by first maximizing what the summary keeps, then trimming. Sub-agents come back in a later lesson; for now, note that they are one more way to keep a window small.

A common mix-up

"If I buy a model with a huge window, I can paste in every manual and stop worrying." It is tempting because the window does fit them. But you would pay for those tokens on every call (Figure 2), and recall gets worse as the window fills. For a small budget, a huge window is the expensive option, not the safe one.

Between sessions: notes as memory 5 min

A session ends. The student comes back next week. What does the assistant know?

By default: nothing. The context window was assembled for that session; when the program stops, it is gone. A new session starts from the system prompt and tool descriptions alone. The student finished the safety training on Tuesday, but unless that fact was saved somewhere and loaded back in, the assistant will ask again.

The fix is an old one, which is why this works: memory is storage outside the context, plus a rule for bringing the right part back in. One pattern Anthropic describes is structured note-taking: the agent "regularly writes notes persisted to memory outside of the context window," and pulls them back in later (Anthropic). Their examples are a to-do list and a NOTES.md file. In their Pokémon-playing example, the agent kept tallies across thousands of steps and, after its context was reset, read its own notes and carried on.

Worked example: the training status

The assistant should remember who completed laser-cutter training. Design it:

  1. Write. When the student passes training, the assistant calls a save_note tool with the student's ID and "laser cutter training done, Nov 4." The program stores it in a file or database.
  2. Read. At the start of the next session, the program looks up this student's record and puts that one line into the context.
  3. Keep it small. Load only this student's notes, not everyone's. Each loaded line is paid for on every call (Figure 2).

Notice that the model is not "remembering" anything. The program writes and loads. The model's part is deciding what is worth saving, and that decision should be in your tool description.

Anthropic also describes a file-based memory tool released in public beta with Sonnet 4.5 (same article). In a first prototype you can build your own version with a single JSON file per student, which fits what you already know from Python.

Retrieval: finding the right page in a long manual 5 min

Notes are things the assistant wrote. Manuals are things it reads. Suppose the band-saw manual is 60,000 tokens. Pasting it into every call would add 60,000 tokens to each of your steps. Instead, the program retrieves only the few passages that bear on the question and puts those into the context.

The standard recipe, called retrieval-augmented generation (RAG), runs in two stages:

  1. Before any question: split each manual into chunks, short passages of a few hundred words, and index them so they can be searched. One search method compares meaning (embeddings); another matches exact words, like the part number "BS-200" (BM25). Anthropic's contextual retrieval post reports that combining the two beat either alone.
  2. At question time: search for the chunks closest to the question, and put the top few in the context.

A chunk can lose its meaning when cut out of its manual: "Replace it every 40 hours" does not say what. The same post prepends a short explanation of where each chunk came from before indexing, and reports that this cut failed retrievals by 35% with embeddings alone and 49% when combined with word matching (Anthropic). A simpler version you can do yourself: store the machine name and section heading with every chunk.

In an agent there is a second option. Rather than the program retrieving before the model runs, give the model a search_manuals tool and let it look things up just in time. Anthropic's article contrasts the two: up-front retrieval is fast, while just-in-time retrieval is more flexible but "slower than retrieving pre-computed data," and agents with poor tools "waste context." They note that many systems mix both, and advise: "do the simplest thing that works" (Anthropic).

ApproachStrengthWeakness
Paste every manual inNothing to buildPaid for every call; recall falls as it grows
Retrieve up front, then answerCheap, predictable, one model callMisses if the first search is poor
Search tool, model decidesCan search again with better wordsExtra calls; can waste context
A common mix-up

"Retrieval makes the model smarter." Not quite; it makes the context better. If the search brings back the wrong chunk, the model will answer confidently from the wrong page, so the quality of your answers can only be as good as the quality of your search. Test retrieval by itself first: does the right chunk come back for twenty real student questions?

Worked example and practice 6 min

Worked example: sort five items

For each item, decide: always in context, saved notes, or retrieved on demand. Use two questions. Is it needed on nearly every call? Does it change between sessions or depend on the student?

  1. "Never book without confirming with the student." Needed on every call and the same for everyone: always in context (system prompt).
  2. The 80-page 3D-printer manual. Needed only for some questions and too long to carry: retrieved on demand.
  3. "Dana finished laser-cutter training on Nov 4." Specific to one student and must outlast the session: saved notes, loaded for Dana only.

Sort these two yourself, with a one-line reason each, using the same two questions: (a) the descriptions of the three tools; (b) a summary of what Dana asked in her last four visits. Then add one budget risk to watch in your design.

Show a solution

(a) Always in context. The model can only choose a tool whose description it can see, and every call needs them. (b) Saved notes. It is student-specific and outlives sessions; load a short summary, not the full transcripts. Budget risk: anything always in context, plus anything loaded at session start, is repeated on every call, so a growing notes file steadily raises the cost of every request. Keep notes short, and summarize them from time to time.

Summary 2 min

  • The model sees only its context window: the text the program sends in one call, including the system prompt, tool descriptions and the answer being written.
  • Between steps, the program resends the transcript, so the window and the cost grow with each step. A bigger window delays the limit but does not stop context rot.
  • Between sessions, nothing is kept unless it is saved outside the window and loaded back. Notes are the simplest memory.
  • Retrieval brings only the few relevant chunks of a long document into the context, and an answer can be no better than what was retrieved.
