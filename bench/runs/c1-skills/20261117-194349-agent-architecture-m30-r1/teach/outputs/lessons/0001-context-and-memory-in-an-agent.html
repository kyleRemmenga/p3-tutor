The context window 5 min

A language model reads text and writes text, as you already know. The context window is everything the model can read in a single call, plus the room for what it writes back. It is measured in tokens, the small chunks of text (often a word or part of a word) that the model actually processes. The window has a fixed size limit in tokens (Anthropic: context windows).

The key idea: the model has no hidden state between calls. If something is not in the window of this call, the model cannot use it. Anthropic's engineering team calls the window's contents the agent's context and describes it as a finite resource: every extra token competes for the model's attention, so the goal is the smallest set of high-signal tokens that gets the job done (Effective context engineering for AI agents).

What is kept between steps 5 min

Inside one request, the agent loop makes several model calls. The model itself remembers nothing from one call to the next. What carries the work forward is the program: it keeps a list of messages (the student's question, each tool request the model made, each tool result, and so on) and sends the whole list again on every call. The Claude API works this way: you supply the full conversation each time (Anthropic: context windows).

So "memory within a request" is just your own list, growing. Here is the shape in Python, as a sketch rather than a working program:

messages = [{"role": "user", "content": "Is the laser cutter free Friday?"}]

while True:
    reply = call_model(system_prompt, tools, messages)   # whole list sent every time
    messages.append(reply)                                # keep what the model said
    if reply is a tool request:
        result = run_tool(reply)                          # the program runs it
        messages.append(result)                           # keep what came back
    else:
        break                                             # final answer

Two consequences follow. First, every tool result you append stays in the list, and so stays in every later call, whether or not it is still useful. Second, whatever you choose to not append, or choose to delete, is gone from the model's view. You control the context; the model does not.

Why the window drives cost 4 min

Models are billed by tokens, input and output. Because the whole list is re-sent on every call, a result that enters the context at step 1 is paid for again at step 2, step 3, and every step after it. Cost does not grow with the number of steps alone; it grows with steps times window size.

That is why Anthropic's guidance is to keep context lean and to let agents fetch information when needed, rather than loading everything up front (Effective context engineering). For a small budget, the cheapest token is the one you never put in the window.

Worked example: pasting the whole manual

Illustrative numbers, not real prices: the laser cutter manual is 120 pages at about 500 tokens a page, so 60,000 tokens. A request takes 5 model calls. Suppose input costs $3 per million tokens.

  1. Paste the manual into the system prompt. Each call sends at least 60,000 tokens, so 5 calls send at least 300,000 input tokens. At $3 per million, that is about $0.90 for one question.
  2. Retrieve three pages instead. Each call sends about 1,500 tokens of manual, so 5 calls send about 7,500. That is about $0.02.
  3. Compare. The same question costs roughly 40 times more with the whole manual pasted in, and the model has to find the right paragraph in a crowded window.

Providers offer prompt caching, which makes repeated, unchanged prefixes cheaper; read your provider's pricing before relying on it. Caching helps, but it does not make a 60,000-token window as focused as a 1,500-token one.

Between sessions: nothing, unless you save it 4 min

A session is one conversation or task from start to end. When it ends, the messages list is gone, and the next session starts with an empty window. The model does not remember the student from last week. Anything the assistant should know next time must be saved by the program in storage that outlives the session, then loaded back into the window.

For the makerspace, the saved store might hold "Riley completed laser cutter training on March 3". At the start of Riley's next visit the program looks this up and places one line in the window. The model does not need to remember Riley; the program remembers, and tells the model.

A common mix-up

"The assistant will remember the student because we talked last time." It is tempting because chat products feel continuous. When a product does appear to remember, a program is saving and re-loading text behind the scenes. A bare model call has no such feature, so your design must supply it.

Retrieval: memory you search 5 min

The manuals are too long and too many to keep in the window. Retrieval means searching a stored collection and putting only the best matches into the window for this call. The usual recipe is retrieval-augmented generation: split documents into chunks (a page or a section each), index them so they can be searched, and at question time fetch the few chunks that best match. Search can be by meaning, using embeddings, by keywords, as in BM25, or both together (Anthropic: contextual retrieval).

A known weakness: a chunk cut out of a manual may lose its context. A chunk saying "Set the speed to 40%" does not say which machine or material. Anthropic's contextual retrieval adds a short explanation of where the chunk comes from to each chunk before indexing, and reports fewer failed retrievals in its tests (same source). A cheap version for you: put the machine name and section heading at the top of every chunk.

In an agent, retrieval is a tool. The model calls search_manuals(machine, query), the program searches, and the top chunks come back as a tool result. That is what you drew in the agent loop; now you can see why the tool exists: it keeps the manual out of the window until a question needs it.

Notes: memory the agent writes 4 min

Retrieval searches material that already exists. Notes are memory the agent writes itself while it works, to read later. Anthropic's engineering post calls this structured note-taking: the agent saves progress and decisions to storage outside the window and pulls them back when needed (source). Anthropic's memory tool is one implementation: the model reads and writes files in a memory directory through tool calls, and your program carries out those file operations, so you decide where the files live (Memory tool docs).

Two related ideas for long tasks, both from the same post: compaction, where a long history is summarized and the window restarted with the summary, and sub-agents, which do detailed work in their own window and return a short result. You will meet sub-agents again when we reach multi-agent systems.

A common mix-up

"Notes are just more context." They are not: a note sitting in a file costs nothing per call. It becomes context only when the program loads it. That is the point of notes, and the risk: a note that nobody loads, or an out-of-date one that is loaded, is useless or harmful.

Worked example and practice 5 min

Worked example

Riley returns and asks: "Can I book the laser cutter Friday afternoon, and what settings for 3 mm plywood?" Decide where each piece of information lives.

  1. Rules for the assistant (be brief, check training before booking): fixed for everyone, short, needed every call. Put them in the system prompt.
  2. Riley's training status: specific to Riley, changes over time, must survive sessions. Keep it in the saved store; the program loads one line into the window at session start.
  3. Friday's calendar: changes constantly and belongs to the booking system. Fetch it with a tool when asked; do not store a copy.
  4. Plywood settings: fixed, long, in the manual. Use retrieval; only the best-matching chunk enters the window.
  5. The conversation itself: lives in the messages list for this session only, and is dropped at the end, apart from anything worth a note.

Summary 2 min

  • The context window is all the model sees on one call: prompt, tools, history, tool results and room for the reply. Nothing outside it exists for the model.
  • Between steps, the program keeps a messages list and re-sends all of it every call, so every token in it is paid for again on each step.
  • Between sessions, nothing persists unless the program saves it and loads it back.
  • Retrieval searches fixed material and brings only a few chunks into the window; notes are what the agent writes during use.
