The idea 4 min

A language model only produces text. It cannot read a file, query a database or check the weather. A tool is a function your own code provides and describes to the model, so the model can ask for it to be used.

The key fact: the model never runs a tool. It only asks. Your application runs the tool and reports the result back. The official docs describe it this way: Claude responds with stop_reason: "tool_use" and a tool_use block holding the tool name, a unique id and structured input; your application executes it and sends the result back (How tool use works).

That gives a loop, called the agent loop:

  1. Send the conversation and the tool definitions to the model.
  2. Read stop_reason. If it is "tool_use", run each requested tool in your code.
  3. Append the model's reply, then a tool_result message carrying the matching tool id, to the conversation.
  4. Send it all again. Repeat until stop_reason is anything other than "tool_use", usually "end_turn".

Each trip around the loop is one separate request. The model keeps no memory between requests, so you resend the whole conversation each time.

Check yourself

The model returns a tool_use block naming get_weather. What has happened so far?

Show the answer

Claude asked your code to run the function. The model only emits the request; your application executes it.

A common mix-up

"The model calls the tool." It is tempting because the SDK hides the loop and it looks like one step. In fact your code executes the tool, so your code controls permissions, errors and limits. That is also why a loop needs its own cap on iterations: a loop written only as while stop_reason == "tool_use" can spin forever if the model keeps asking.

An example 2 min

A shopping assistant has two tools: find_price(item) and get_budget(). The user asks: "Can I afford a keyboard?"

Request 1  user: "Can I afford a keyboard?"
Reply 1    tool_use: find_price("keyboard")        stop_reason: tool_use
           (your code returns 45)
Request 2  ...history + tool_result: 45
Reply 2    tool_use: get_budget()                  stop_reason: tool_use
           (your code returns 60)
Request 3  ...history + tool_result: 60
Reply 3    "Yes, 45 is under your 60 budget."      stop_reason: end_turn

Walking through it 3 min

Worked example
  1. Reply 1 ends with tool_use: the model could not answer without a price, so it asked. The loop continues because the stop reason is tool_use.
  2. Your code runs find_price and returns 45 inside a tool_result that repeats the request's tool id. The id lets the model match results to requests.
  3. Request 2 carries the full history. Without it the model would not know what it asked.
  4. Reply 2 asks for the budget. The model chose this on its own; no code fixed the order. That freedom is what separates an agent from a fixed workflow, where code decides the steps (Building effective agents).
  5. Reply 3 ends with end_turn: the model has enough, so the loop exits and you show the text.

Two tool calls gave three requests: the final answer needs one more request than there are tool calls.

Summary 1 min

  • The model asks for tools; your code runs them.
  • The loop continues only while stop_reason is "tool_use", and resends the full history each time.
  • Results go back with the matching tool id.
  • Add an iteration cap so a loop cannot run forever.
